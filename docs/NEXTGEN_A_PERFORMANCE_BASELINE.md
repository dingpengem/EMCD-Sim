## Modeled large-output memory (not measured)

Let `P=128²` scan positions, `D=128²` detector pixels, `E=243`. One dense
observable contains `P*D*E = 65,229,815,808` elements. GiB/TiB below use powers
of two; these arrays were never allocated.

| Stored object | Bytes per element / multiplicity | Size |
|---|---|---:|
| One dense intensity | float32, 4 | 260,919,263,232 B = **243 GiB** |
| One dense amplitude | complex64, 8 | **486 GiB** |
| Current-precision real / complex equivalent | float64 / complex128 | 486 / 972 GiB |
| Float32 intensity with 128 interaction-depth bins | ×128 | **30.375 TiB** |
| Complex64 amplitude with 128 depth bins | ×128 | **60.75 TiB** |
| Float32 depth data, 2 reversals ×2 methods ×2 channel modes | ×8 | **243 TiB** |
| Four detector/reversal reduced spectra `(P,E,4)` | float32 | 60.75 MiB |
| Twelve raw/derived spectra `(P,E,12)` | float32 | 182.25 MiB |
| Four reduced spectra retaining 128 depths | float32 | 7.59375 GiB |

The 243/486 GiB cases each describe one quantity, not an all-inclusive result.
Actual production precision is float64/complex128; float32/complex64 is a future
storage/backend scenario requiring numerical validation, not permission to
downcast current output. Magnetic reversal, groups/sites, methods and selected
diagnostics multiply retained storage independently when requested. Derived
ratios should usually be regenerated from parent raw signals instead of storing
many complete duplicate cubes.

Illustrative future tile: 16 probes, 32 outgoing detector directions, four
energies, 128 slices on a 128² wave grid, complex64/float32 only for this model.

| Buffer / algorithm choice | Size |
|---|---:|
| One complex64 wave | 0.125 MiB |
| Incoming history, 16 probes ×129 nodes | 258 MiB |
| Outgoing full history, 32 directions ×129 nodes | 516 MiB |
| Outgoing streamed current states, 32 directions | 4 MiB |
| 16 probes ×4 energies ×3 transition modes ×2 reversal wavefields | 48 MiB |
| 128 real potential slices | 8 MiB |
| Five energy-specific transmission sets ×128 slices | 80 MiB |
| If materialized: response `(16,32,4,128,3,3)` | 18 MiB |

A possible streamed-adjoint policy stores incoming histories, one outgoing
batch, potentials/transmissions, an 18 MiB response tile and small buffers:
about 368 MiB before FFT workspaces, allocator pools, inputs and output staging.
The 48 MiB forward-event buffer is an alternative path, not automatically added
to an adjoint-only implementation. Keeping outgoing histories adds 512 MiB
relative to streaming. Recompute/checkpoint policies can reduce histories at
additional CPU cost. Simultaneous host/device copies can roughly double resident
wave buffers; FFT libraries may require substantial plans/work areas. These
are modeled policy choices, not measured GPU memory requirements. Additional
site/event modes or partially coherent incident components multiply the relevant
batch, not necessarily every saved output axis.

## Optimization priorities and acceptance limits

1. Preserve complex amplitudes, post-loss energy, source validation, excluded
   support diagnostics and current numerical contracts. Reuse prepared geometry,
   incoming states and source tensors only with complete immutable context keys.
   Current code already reuses incoming and grouped outgoing work.
2. For new localized/probe work, measure outgoing response/FFT and event-mode
   batching; compare direct versus reciprocal/scattering-matrix reuse under the
   same physical model. Optimize an observed workload, not this noisy micro-matrix.
3. Stream detector/event reductions and bound memory before introducing large
   scan outputs. Array allocation/copy costs are a plausible future issue but
   were not isolated here. No benefit magnitude is claimed.
4. Consider GPU FFT/linear algebra only after an explicit resident-state boundary
   and a sufficiently large independently validated CPU case exist. Device
   transfer, FFT-plan/pool memory, batching and precision can dominate small jobs.
   There are no GPU measurements or speedup estimates in this report.
